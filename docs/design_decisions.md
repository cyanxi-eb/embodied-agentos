# 设计取舍（为什么这么做）

## 1. 为什么用行为树，而不是纯状态机？

* 状态机适合「阶段互斥」的流程（审批流、会话状态），但技能执行是**带恢复策略的层级结构**：先执行、失败重试、再失败回退、最后才请求重规划。
  py_trees 的 Selector/Sequence + 自定义 Retry 天然表达「优先级恢复分支」，新增恢复策略是加一个子树，而不是在状态机里加交叉边。
* 状态机无法复用「前置条件 → 执行 → 后置条件」这条固定骨架；行为树可以把骨架封装成子树，每个技能只提供契约。
* 主循环（LangGraph）负责**跨技能**的任务级决策，行为树负责**单技能内**的执行恢复，分层后职责清晰、可独立测试。
  纯状态机会把两件事混在一个大图里，失败归因困难。

> 「行为树承载技能执行与恢复分支」这件事，本项目在 Python 侧用 `py_trees` 实现；
> 真实部署可以在 C++ 侧用 BehaviorTree.CPP 实现等价树，ROS2 侧代码与文档给出了对齐方式。

## 2. 为什么模型只选技能、不直接下发速度？

LLM 的强项是**语义分解与选择**，弱项是**连续控制与安全约束**。让模型直接输出 `cmd_vel` 会带来三个不可控风险：

1. 无法做参数级校验（速度/坐标/超时都不在 schema 内）；
2. 无法保证安全边界（限速/围栏/急停只能事后补救）；
3. 无法回放与评测（没有技能级语义，失败无法归因到「导航失败」还是「抓取失败」）。

因此接口设计成：模型只能从 8 个技能里选一个并填 JSON Schema 参数；网关对技能名与参数做拒绝名单；
坐标走电子围栏；速度由后端在网关裁剪后集成。模型输出的错误会表现为失败码（`NOT_FOUND`/`BLOCKED`/`PRECONDITION_FAILED`），可被重规划消费。

## 3. 为什么后置条件要独立于技能返回值？

「模型说完成了」和「机器人真的完成了」是两件事。三层防线：

1. 技能返回结构化结果（可失败、带失败码）；
2. 行为树对世界状态求值后置条件（技能自报成功但世界不满足 → `POSTCONDITION_FAILED`）；
3. LangGraph `verify_postcondition` 节点**再次**独立求值（图节点是最终权威），再叠加评测器的 ground-truth 检查。

消融实验（关闭 verify+replan）在故障注入场景恢复率显著下降，说明这套校验不是装饰。

## 4. 为什么安全网关放在「进入 ROS2 之前」？

安全策略必须与执行器解耦：同一份网关同时保护 2D 仿真与 ROS2 真机；如果放到底盘驱动里，上层仍然可以绕过。
网关做**统一裁决**（拒绝/裁剪），执行器保留**最后防线**（差速模型再 clamp 一次，ROS2 侧 speed limit 再限一次），纵深防御。

电子围栏/闩锁急停/拒绝名单都是「拒绝后世界状态不变」的纯判断，便于单测；超时守卫用可注入时钟，仿真用 sim clock、真机用 monotonic clock。

## 5. 为什么用确定性 2D 仿真而不是 Gazebo？

要让**全部评测数字可复现**，就得有一个纯 Python、无 GPU、不依赖 ROS2/Gazebo/WSL 也能毫秒级跑完的确定性环境。2D 仿真正好满足这个条件。
物理保真度低（抓取是确定性事件）是它的短板，但它足以验证本项目真正要证明的东西：**规划-执行-校验-重规划的整条链路、技能契约、安全边界、可观测性**。
Gazebo/ROS2 适配层保持完整代码与文档，明确标注没跑过，避免「假装真机验证」。

## 6. 为什么 Qdrant 用 local 模式 + hashing embedding？

* Qdrant local 模式（`QdrantClient(path=...)`）无需服务端，数据落 `.cache/`（git 忽略），接口与远程模式一致，换真实部署只改构造函数。
* hashing embedding 是确定性 bag-of-features，不下载模型、可离线复现；代价是语义泛化弱。记忆检索再加**payload 精确匹配**（颜色/类别/场景）与分数阈值，避免「相似但错误的物体记忆」导致静默错误计划（见 failure_cases #4）。
* 记忆真实影响计划：`plan` 节点优先用「上次看到该物体的坐标」导航；检索结果也进 trace 与评测（命中率/命中时成功率）。

## 7. 为什么暂停只在技能边界？

连续运动中暂停需要保存控制器内部状态（路径、代价地图、goal handle），跨进程恢复几乎不可能保证一致。
在 `dispatch_skill` 边界暂停，checkpoint 里有「任务图 + 已完成结果 + 世界快照」，恢复只需重建仿真世界/重新下发下一个技能 goal；
安全语义也更好：不会出现「半条腿在动、半条腿停」的状态。代价是暂停延迟最多一个技能（仿真里秒级）。

## 8. 为什么评测用规则 planner？

没有 GPU / API key 的环境里，LLM 输出不可复现，成功率一掉你没法判断是系统坏了还是采样波动。
规则 planner 让 450 幕评测能重复、能在 CI 里跑；`LLMPlanner` 照样实现，只是标注成可选真实后端。
所以这份仓库里凡是写「规划」的地方，指的都是规则 planner——换成 LLM 规划器时，指标得另出一份，不能混着说。

## 9. 已知取舍与代价

| 取舍 | 代价 | 缓解 |
| --- | --- | --- |
| 2D 仿真代替物理仿真 | 抓取/感知过于理想 | 故障注入 + 感知漏检/噪声接口 + 文档声明 |
| 规则 planner | 语言覆盖有限 | 明确词表；LLM planner 可选接入并做 schema 校验兜底 |
| Qdrant local + hashing | 语义检索弱 | payload 精确匹配 + 分数阈值 + 记忆只作「提示」 |
| 暂停在技能边界 | 暂停延迟 | 任务级暂停足够；真机连续暂停需控制器状态管理 |
| ROS2 未运行 | 不能声称真机可用 | 代码+包骨架+文档，README 显著声明 |
